## Branches and releases

- `main` = production. Commits here ship; each release is tagged `vX.Y.Z`.

```
python3 pack.py --dev     # dev flavor only, for testing while on dev
python3 pack.py           # both flavors
python3 pack.py --prod    # prod flavor only, for a release built from main
```

The dev flavor is named `bugtongph-dev`, every command prefixed (`.dev-script`), and it is

the manifest `defaultPrompt` starters.

Never edit an installed copy. Bump the version on every install, or the host serves the
previously cached copy.

## Non-negotiables

1. **One question, one artifact, then stop.** Never two stages in one turn, never the whole
   pipeline at once.
2. **Explicit trigger only.** Ordinary conversation never advances a stage or spends a
   generation.
3. **≥3 options everywhere**, **option 1 marked `(suggested)`**, and the options must be
   wildly different from each other — different direction, not different wording. If two
   options could be described by the same sentence, they are one option.
4. **Any correction returns to OVERVIEW and waits**; multiple rejections queue as PENDING
   FIXES and are handled upstream-first.
5. **The riddle comes from Notion only.** Never model memory, web search, or a generated
   riddle. Preserve stored wording exactly. Keep the answer operator-only — it must never be
   indicated in any audience-facing output.
6. **Every clip is 8 seconds.** One clip holds ~11 words of speech. Count the riddle's own
   words first; over ~9 words it cannot share a clip with a reaction, so most episodes are 2
   clips. Never state a duration without its clip count and its arithmetic.
7. **The status line is the stage line only.** No channel, release, or workflow.
8. **Veo 3.1 Lite is the only target.** Veo 3.2 is not in Flow; do not target it.

## Current pipeline

Two content pipelines differ only in their first stage; everything after is shared.

```text
riddle: RIDDLE -> LOCATION -> ENVIRONMENT -> PROFILE -> SCRIPT -> FRAME -> OVERVIEW
               -> IMAGE PROMPT -> IMAGE -> CLIPS
topic:  TOPIC  -> LOCATION -> ENVIRONMENT -> PROFILE -> SCRIPT -> FRAME -> OVERVIEW
               -> IMAGE PROMPT -> IMAGE -> CLIPS
```

| Stage | Offers | Locks |
| --- | --- | --- |
| RIDDLE | 5 Notion records | exact stored wording, operator-only answer |
| TOPIC | 5 model-invented topics | the topic and its angle only — no riddle, no answer, no Notion |
| LOCATION | 3 places | the place only — no weather, no light |
| ENVIRONMENT | 3 condition sets | time, weather, light, atmosphere, ambience |
| PROFILE | 3 bundles | character + art style + voice as **one** choice |
| SCRIPT | 3 scripts | dialogue + actions, beats, ending state, the 8s budget (last creative choice) |
| FRAME | panel count 2–5 (default 2–3) | the ingredient-sheet panel plan, text only |
| OVERVIEW | — | shows everything locked; the hub every correction returns to |
| IMAGE PROMPT | — | the prompt formula, text only (cheap gate before generation) |
| IMAGE | — | binds the reference asset, generates, validates |
| CLIPS | — | shot plan + copy-ready Clip 1 (Ingredient, 8s) and Clip 2 (Extend) prompts |

RIDDLE is the default; TOPIC runs only on `.topic` or `.auto topic` / `.auto fresh topic`
(`.vlog` and `.vblog` are aliases for `.topic`).

`.auto` is the unattended mode: takes option 1 at every gate, stops once the image is generated
and validated. CLIPS runs only on request.

value across the whole tree — stale duplicates have shipped before (an old pacing figure
survived in three files after the first fix).

## Adding a new pipeline stage or feature

Touch every one of these, in this order:

1. **New reference** `references/<stage>.md` — what it offers, how many options, what it locks,
   what it must never do.
2. **`SKILL.md`**, five places, all of which must stay in sync:
   - §1 stage-order block (line ~26)
   - §3 `.auto` composition block (line ~106)
   - §6 stage contracts — add the section
   - §8 status line
   - §11 commands — add the command and its correction form
   - §12 load-when table — add the row, or the file is invisible to the model
3. **`references/reroll-and-options.md`** — the option-count table, the reroll trigger, the
   stage's command in the correction list.
4. **`references/runtime-state.md`** — the stage list, its checkpoint field, its place in the
   invalidation cascade.
5. **`references/overview.md`** — the stage's line on the OVERVIEW screen, and its position in
   the upstream-first fix order.
6. **Manifest** `plugin.json` and `.codex-plugin/plugin.json` — command list in the
   description, and a version bump. If the command set changed, check the `defaultPrompt`
   entries: they are capped at 128 chars and the host silently drops over-long ones, then keeps
   the first 3 survivors.
7. **`README.md`** (pipeline line, command list) and **`CHANGELOG.md`** (new version section).
8. **Build and verify:**

```
python3 validate-plugin.py bugtongph
python3 pack.py
python3 ~/.hermes/skills/software-development/codex-plugin-packaging/scripts/verify_plugin_install.py dist/bugtongph-<version>.zip
python3 ~/.hermes/skills/software-development/codex-plugin-packaging/scripts/verify_plugin_install.py dist/bugtongph-dev-<version>.zip
```

Green means: manifest parses, both skills resolve (`<plugin>:<skill>`), the app reference
resolves with an `installUrl`, icons are absolute, and the intended `defaultPrompt` entries
survive. A green local validator is not host proof — run the probe against the archive.
